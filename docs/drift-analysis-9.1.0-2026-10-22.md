# 漂移复核与 9.1.0 准备 — 2026-10-22

本轮确认并修复了 Criterion 的准备数据生命周期问题、验证结果消费问题，以及
增量更新中可直接消除的计算和初始化开销。完整 Linux 发布验收仍未通过；这些改动
不能代表已经解释了 #2897 的全部服务时间漂移。

## 已确认的基准问题

Criterion 0.8.2 会在预热和每个测量样本中重新调用 `bench_function` 回调。
原 `bench_update` 把 `old_data` 的整份克隆、引用 Vec 和变更列表放在这个回调里。
这些操作虽在内层计时之外，仍会反复更换输入持有者、分配状态和缓存状态。
独立源码副本只在真实准备语句处添加计数：原六个稀疏场景每次构建 **14～21 次**，
修复后各 **1 次**。构造计数测试使用短时间配置，只证明生命周期，不证明速度。

最终基准直接借用已有不可变原始分片，引用和变更列表只准备一次；Classic 与 Leopard
编码的可变输入也在整个基准中保留一次。验证布尔值交给 `black_box` 消费，防止丢弃
结果使比较工作变成无用计算。恢复基准原有每次克隆、缺失输出和释放政策保留。

更新基准现在覆盖三个几何、一个/两个变更、稀疏/稠密两种输入和两种输出生命周期，
共 24 个场景：

- `throughput_matrix_update`：每次仍克隆并释放输出，包含真实的调用者开销。
- `throughput_matrix_update_in_place`：输出持有者和引用向量复用，每次执行合法的
  正向或反向变更。跨越奇数次迭代的样本仍保持正确状态，结束后核对全部 parity。

原稀疏 case 名保留，稠密 case 增加 `_dense`。两种生命周期不能互相冒充版本收益。
速率分母沿用逻辑完整 stripe 字节数，应同时查看每次调用耗时；它不是内存总线带宽。
profile JSON 升为 schema 2，增加完整 `benchmark` 标识，并只导出实际执行的基准，
避免不同变更数/输入分布重名，或把被过滤的 case 当成已测量。

## 运行时收敛方案

`update` 仍先验证全部计数和长度，包括重读后变空的泛型视图，再进入计算。
通用矩阵路径现在执行：

1. `None` 更新直接成功；显式提供的相同分块也跳过 parity 核。
2. 首个不同分块才申请一份受现有串行分块政策限制的 scratch。
3. `clear/reserve_exact/extend` 直接写入差分值，不先填零再覆盖；短尾只暴露已写入元素。
4. 直接读取不可变矩阵系数，在对应输出区间累加；不建立行视图、不增加缓存或公共 API。

单 parity 的快速路径保留直接 XOR 和零 scratch，未用本轮稀疏矩阵结果推导其速度收益。

这是安全的 Vec 初始化路径，没有新增生产 unsafe 或未初始化切片。
比较相同分块仍需要读取输入；稠密输入保留原渐近复杂度，故基准同时保留稠密场景。

| 可复算检查 | 修改前 | 最终实现 |
| --- | ---: | ---: |
| GF8，65,553 元素，仅末尾 17 元素块不同：差分 `add` 调用 | 65,553 | 17 |
| 同场景，传入两个 parity mul-add 核的元素总数 | 131,106 | 34 |
| scratch 的字段零值初始化调用 | 1 | 0 |
| 通用矩阵路径 `Some(old)` 完全相同的更新申请 | 1 | 0 |
| GF8，33 parity/65 元素、有变更的申请量 | 2 次 / 593 B | 1 次 / 65 B |

前两项是测试 Field 计数器所观测的 API 计算量，不是硬件乘法指令数或耗时倍数。
反例先在旧实现失败，再在最终实现通过；完整重编码逐元素对照保护结果。
原正常格式 200-case 兼容性范围和历史 fast/custom 边界保持。

## 固定二进制服务诊断

在修改稀疏更新之前，预声明了一次完整的本机诊断：6 个原场景、每个形状固定计数、
每 worker 三次预热和九个样本，36 个新 worker 共 432 个观察。原完整调用、分段观察、
复用输出分别正序/逆序执行。二进制、源码、编译器和输入冻结，未在采样间构建。
全部原始数值私有保留，公开[描述性汇总](../benchmarks/incremental-update/2026-10-22/service-summary.json)。

原完整调用的两个同版重复超过 5% 参考线；复用输出的六项重复均在约 1.3% 内。
分段观察中，复制输出约占单变更调用的三分之一，释放本身相对较小。分段计时有观察
开销，且调用者生命周期不同，不能把两类绝对耗时相减当成版本提升。

采样点的线程运行时间接近墙钟时间，major faults 为零；CPU 查询结果在几个编号间
变化，但查询端点不是 CPU 绑定证明，也未获得可靠的编号到核心类别映射。
当前主机还观察到并行编译；这只证明当前环境没有隔离证据，不能反推历史全部漂移
均由它造成。频率、缓存/内存服务和其他宿主活动仍未唯一分离。

该诊断的窗口、计数选择和放置条件均不等于正式采样协议。它修正了此前只有均值而
缺少服务信息的证据边界，不产生发布放行或候选速度归因。

## Linux 失败 case 的授权只读复算

从原 A1 的 `small_file` 文件提取该 case 的全部 12 条记录：3 个预热、9 个正式样本，
每条均为原来的 262,144 次迭代。原始数值和逐条分析保持私有；公开
[来源绑定的衍生汇总](../benchmarks/incremental-update/2026-10-22/linux-failed-case-replay-summary.json)。
原文报告中相同 case 字符串还出现在 `smoke`，因此复算始终同时绑定 profile 与 case，
不能把另一 profile 的 1.1034% 分布误作本次失败的结果。

现有共享验证器核对了完整顺序、版本、计数、原始耗时、时长下限、工作负载、
放置声明、调用者布局和逐观察契约。重新计算的中央跨度为 **20.6527515206%**，
与原 `small_file` 报告精确一致，仍超过 10%。片段自洽性检查不等于重新验证完整
校准、冻结计划或外部资源隔离，也没有执行候选阶段、重复门禁或逐布局验收。

| 九个正式样本的观测 | 复算结果 |
| --- | ---: |
| 调用线程每次迭代运行时间的中央跨度（独立排序） | 20.6357% |
| 调用线程 run / wall 范围 | 99.9698%～99.9982% |
| 最大调用线程 runnable wait / wall | 0.0097354% |
| wall 与内部 timed 差额 / wall 范围 | 0.0000161%～0.0000320% |
| 整个进程 minor / major faults | 0 / 0 |

原时间顺序中，三个预热和开头的正式观察较慢，随后正式观察的运行成本下降。
差额不是可据此删除的异常值，也没有足够信息将变化命名为“预热不足”。
全部 12 条记录均保留；没有追加预热、裁剪两个慢样本或改变计数后重新宣称通过。

这些量支持的判断是：变化包含原操作窗口内调用线程的执行服务变化，已测量的
调度等待、缺页与计时边界差额不能解释其幅度。正式 `reconstruct` 循环仍包含每次
克隆、丢弃缺失分片、恢复输出及释放；不能将该窗口称为纯 decoder 耗时。
固定调用者布局并不证明每次新输出、内部矩阵和物理页面/缓存状态相同。
没有逐样本频率、缓存或物理宿主见证，故具体机制仍不能唯一确定；之前修复的
Criterion 回调准备也不在这个正式工作循环中。

现有 `analyze_baseline_variability.py` 复用原记录与验证路径，新增 `measured_service`
汇总以及逐条每次迭代运行成本、wall/timed 差额。各信号独立排序；不同计时边界的
比例保留原值、不裁剪到 1，零运行时间保留未知跨度。三项新反例覆盖时间序列变化、
信号排名不同及零计数，完整 Python 门禁共 375 项通过。分析器未接入正式采样器，
没有新接受门槛、远程观察线程或生产代码改动。

后续有区分力的工作必须先确定可观察的受控条件：逐样本执行速率/缓存见证，或经
核验的物理宿主资源控制。已有 guest CPU 分区不能替代物理缓存/内存带宽隔离。
仅在同一条件重跑完整矩阵、扩大预热或替换分配器，均不能证明修复了这次失败。
条件确定后，保留原完整基线资格及最终 ABBA/布局流程，不以单 case 诊断代替验收。

正式 126-case 采样器、操作循环、放置检查和全部门槛未改：校准目标 2 s 墙钟/
100 ms timed，样本下限 1 s/40 ms，中央分布 10%、同版重复 5%。
本机 Criterion 和描述性服务诊断都不替代这些门槛。
