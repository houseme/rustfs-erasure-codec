## 合并执行视图，保留既有恢复路径

原执行器通过 SmallVec::new 逐项收集引用，超过 32 项时按增长策略申请容量。
例如 33 项输入会申请 64 项空间。组合式选择性 bulk 恢复还先建立 parity 表，
再把它扩展进 data 表，宽 parity 布局因此多出一张临时表及合并时的容量增长。

两个既有 Classic 执行器现在从计划已知的 survivor、data target 和 parity target
数量直接预留容量。泛型路径只在普通混合恢复需要重读已恢复 data 时预留其引用表，
data-only 和组合式路径保留零容量。32 项以内继续使用原内联空间，无输出仍提前返回。

bulk 路径在 shard 索引升序遍历时，直接把组合式 data/parity 输出收集到最终同一张表。
所有 data 索引均早于 parity，顺序与旧的两表合并相同；执行时继续使用原组合系数行、
批量内核及并行决策。阶段指标改用计划中两个原始目标数量，避免合并后把 parity
计为 data，尤其保证 parity-only 请求没有 data 阶段。

泛型目的地仍逐项初始化、完成并发布。没有增加第二套恢复算法、unsafe、长期借用、
全局缓存或公共 API。完整 64 个 src 成员与 Cargo/build 三个成员中，仅 reconstruct.rs
发生变化；其两个执行器以外的前后内容逐字节相同。planner、矩阵、字段/原生内核、
编码循环和并行策略保持不变。

## 完整申请对照

[完整资源目录及源码绑定](../benchmarks/global-review/2026-10-26/recovery-view-resources.json)
保留前后版本各两种特性构建的全部 432 个计数窗口：每构建泛型 GF8/tower GF16
各 12 布局、三次重复，加 GF8 bulk 12 布局、三次重复，共 108 个窗口。
同一份最终测试逐字节用于前后构建，采用 release、std+SIMD，指标分别关闭和开启。
两种特性的申请结果相同，每布局三次结果一致。

计数包含 alloc/alloc_zeroed/realloc 次数及完整 requested bytes；realloc 按新目标大小计。
计划、参考编码和调用者 backing buffers 在计数外准备，每项先预热一次。
所有 present/请求输出核对参考字节，未请求 erasure 保持 missing，泛型 backing buffer
还检查 dirty sentinel。没有只采集有改善的布局。

下表为每调用的元数据申请次数 / 字节。泛型两字段结果相同，bulk 的目标 payload
另列在完整记录中，未从总申请中隐藏。

| 布局 | 泛型：此前 → 当前 | bulk 元数据：此前 → 当前 |
| --- | ---: | ---: |
| narrow，4+3 | 0 / 0 → 0 / 0 | 0 / 0 → 0 / 0 |
| input32，32+3 | 0 / 0 → 0 / 0 | 0 / 0 → 0 / 0 |
| input33，33+3 | 1 / 1,024 → 1 / 528 | 1 / 1,024 → 1 / 528 |
| input64，64+3 | 1 / 1,024 → 1 / 1,024 | 1 / 1,024 → 1 / 1,024 |
| parity32，2+33 | 0 / 0 → 0 / 0 | 0 / 0 → 0 / 0 |
| parity33，2+34 | 1 / 512 → 1 / 264 | 2 / 2,048 → 1 / 528 |
| parity64，2+65 | 1 / 512 → 1 / 512 | 2 / 2,048 → 1 / 1,024 |
| all_data_mixed，33+34 | 3 / 2,560 → 3 / 1,320 | 2 / 2,048 → 2 / 1,056 |
| all_data_only，33+34 | 2 / 1,536 → 2 / 792 | 2 / 2,048 → 2 / 1,056 |

例如 parity33 的 bulk 仍需新建 33 个 65 B 输出，payload 为 33 次 / 2,145 B。
加上引用表，总计从 35 次 / 4,193 B 降到 34 次 / 2,673 B。
wide_parity_mixed 的总计从 37 次 / 5,282 B 降到 36 次 / 3,282 B。
这些是申请请求成本；没有把它解释为相同比例的耗时、RSS 或存活峰值下降。

计数使用串行 prepared workspace。另在 4 线程池、max_parallel_jobs=2 下，检查
2+34 parity-only 与 33+34 混合请求，分片长度 512 KiB+65。指标开启的前后构建
均实际进入 code_some 并行分支；所有请求输出、未请求状态和阶段计数正确。
该契约只提供并行路径的功能见证，没有测量其申请或速度。

既有标量观察字段的长度 1/65/4097、各三次操作数在前后和两种特性构建间相同；
复用计划仍执行 4*N 次乘法、3*N 次加法。没有改变恢复算术。

## 回归与诊断边界

同一新测试在此前源码上完成全部 108 条记录后，仅两项新资源预算预期失败，
其余 17 项通过。候选的首次完整回归另有两项旧分配断言失败：它们依赖
32→64→128 的容量增长或固定 64 项表大小，不能识别当前精确容量。
本轮把断言改为计划长度，并加强总申请校验：泛型检查唯一输入表及元数据总次数，
bulk 同时检查次数和完整字节预算。保留 93 个旧 bulk 布局、三矩阵、最高 96 data。
没有删除或忽略测试；首次失败日志摘要和最终通过记录均保留在证据中。

新增 GF8/tower GF16 宽布局短目的地契约：第 33 个 data backing buffer 长度错误时，
此前已完成的 32 个 data 保持正确/present，失败 data 与尚未开始的 parity 保持
missing/dirty，覆盖完整和选择性计划。

stable Rust 1.99.1 / macOS ARM64 最终验证：

- 全工作区全特性 960 项通过，43 项原有忽略；按顶层进程最终汇总排除子测试重复。
- 独立 no_std+SIMD 库 273 项、workspace 契约 12 项通过。
- release workspace 契约 19 项、既有 GF8 workspace 契约 14 项通过。
- 发布版 9.0.0 与当前 9.1.0 的 200 个非 fast 配置精确 parity、双向恢复及历史向量通过。
- verify-scratch 3 个、stream-core 4 个、dynamic 9 个成员实际生成；每个副本 29 项
  功能契约通过。dynamic 的精确摘要重新绑定，另两个摘要保持不变。
  注入副本排除四项资源计数测试，计数来自未注入构建；正式生命周期采样目录未扩展。
- x86_64 Linux 全特性库、WASM no_std+SIMD 库交叉检查、严格 Clippy、格式和 diff 检查通过。
- JSON 与 package allowlist 审计通过：核心包 71 成员、WASM 包 6 成员；本轮测试、
