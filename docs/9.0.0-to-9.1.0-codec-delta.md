# What changes from 9.0.0 to 9.1.0

The algorithm families and normal encoded format are unchanged. The existing
executable links the actual published 9.0.0 crate and the candidate: all 200 normal
format parity/roundtrip cases match byte-for-byte. The additional 15 API resource
scenarios also compare complete parity bytes across versions and verify recovered
data. These checks explicitly disable `fast_one_parity`; they do not promise
recovery of historically inconsistent fast/custom/mixed-entry codewords.

The production implementation was compared at published commit `9891dbe4cfc0b8aaf46b1011bfe9d8de334b51b6` and main
`722064f45862ce90d55d63a1e5a17cbd12a3e9ab`. The measured resource program is `a6184b79ddb8bd54c4038c3c6d21b61323958746`; its production `src`, build
script, manifest and lock objects are identical to that main. The provenance and
complete raw repetitions are retained [alongside this report](../benchmarks/release-compatibility/2026-10-19-resource-delta/provenance.json).

| Area | Material implementation change |
| --- | --- |
| Classic recovery | Share one checked shape/plan across ordinary, optimized, workspace and stream routes; construct plans in their execution storage, borrow coefficient rows and retain decoded views only when parity depends on them. |
| Matrix storage | Initialize final SmallVec storage directly rather than allocate/copy/free a temporary Vec for inline matrices. This affects construction and uncached inverses; warmed inverse-cache hits already avoid inversion. |
| SIMD encoding | Prepare checked native views and select dispatch once per operation; bound common metadata and enforce actual job/chunk budgets. NEON fusion shares input loads/nibble extraction. No new finite-field polynomial or default matrix is introduced. |
| Leopard GF8/GF16 | Reuse bounded per-thread plans/work, avoid unnecessary retained-plan eviction and convert GF16 decode inputs in chunks. Warm calls issue fewer temporary heap requests. Retention is a tradeoff: relevant encoder work caches are capped at 4 MiB per family/thread; request counts are not RSS measurements. |
| Streaming | Reuse initialized block buffers, actual lengths, verification scratch and recovery plans; borrow logical prefixes and reserve legacy Cursor output after validated writes. |
| API and correctness | Add effective encoding-format identity and independent reader/writer recovery. Preserve custom matrices when cloning, reject incompatible workspaces/invalid shapes and make fast single-parity entry points use one consistent XOR matrix. These correct old inconsistent behavior; they are not a new default wire format. |

## Direct request-count differences

Both native macOS ARM64 (`rust-neon`) and Linux x86_64 (`rust-gfni-avx512`) use
Rust 1.99.1, release builds, `std + simd-accel`, four requested Rayon threads and a
four-job cap. They produce identical complete request-count records for all 15
scenarios and every repetition. This is not an ARM Linux or downstream throughput
result. The selected GF8 backend label is not a trace of every internal kernel.

Each API warms twice and retains all three measurements. Caller creation, clones,
reader/writer adapters and output reservation occur outside counting. Missing Vec
outputs allocated by the API remain counted. The cold-inverse cases explicitly
disable the inversion cache. Counts include allocation and reallocation requests
across synchronous operation threads; bytes sum allocation sizes and full realloc
target sizes. They are neither peak live memory nor elapsed-time measurements.

Reproduce from the source repository with a new output filename:

```sh
RUSTUP_TOOLCHAIN=stable RAYON_NUM_THREADS=4 RS_PARALLEL_POLICY_MAX_JOBS=4 RUSTFLAGS='' \
  cargo run --locked --quiet --release \
  --manifest-path scripts/release-compatibility/Cargo.toml --target-dir target \
  -- --allocation-report /path/to/new-resource-report.json
```

The counter is confined to the auxiliary, non-published comparison executable.
No allocator, production algorithm or formal sampler changes. The optional report
refuses to overwrite existing results, has a complete fixed catalog, asserts byte
and recovery correctness, and always records `latency_claim=null` and
`release_approval=false`. Ordinary CI preserves this report as a resource artifact.

## Targeted capture repair and remaining release boundary

The formal evidence controller previously generated both source overlays without
an ownership/finally scope. A failed build or operation left generated integration
sources behind, so a new capture refused to start; even successful captures left
them present. Completed numeric observations only existed in raw logs when a
profile failed before returning. Runtime-context rejection also preceded the
structured row write.

The controller now reuses the existing exact-ownership context for both checkouts,
releases byte-identical generated inputs on success and Python-handled failures,
and preserves foreign/modified files. Worker failures and handled interrupts save
completed sample/timing journals; malformed journals stay rejected with raw logs
and extraction errors retained. Complete rows are written before rejecting changed
runtime context. A passing report is written only after safe overlay cleanup succeeds. Ten lifecycle tests cover these boundaries; the original main
reproduces the build-failure leak and the fixed suite passes. No claim is made
that Python finally can run after an uncatchable process kill or power loss.

This fixes capture cleanup/retry and evidence retention. It is not a demonstrated
cause or cure of the residual elapsed-time drift. No new timing cohort was run.
The existing rejected campaigns still do not establish a trustworthy percentage
throughput difference between versions. Backlog #2897 still needs its remaining
layout/workload coverage and accepted paired performance evidence; request counts
cannot replace those gates or strict positive release preflight.
