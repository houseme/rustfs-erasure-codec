# AArch64 no_std GF16 locator reduction

GF16 error-locator construction multiplies two `u16` values modulo 65,535
for each transform entry. In AArch64 `no_std` builds the product is now reduced
by folding its upper 16 bits into its lower 16 bits and conditionally
subtracting the modulus. Since 2^16 is congruent to one modulo 65,535, this
produces the same canonical remainder. The product fits in `u32`; the folded
sum is at most 131,069, so one subtraction is sufficient. Zero remains zero.

The change is restricted to AArch64 `no_std`: standard builds and other targets
retain their original loop. It changes neither public API nor serialized shard
bytes, cache behavior, or destination publication. The baseline source was
`5703a27`; subsequent changes before this commit did not change codec or xtask
sources. The implementation and diagnostic digest update are in `004d824`.

## Performance observations

The [AArch64 no_std comparison](../benchmarks/gf16-locator-reduction/2026-11-01/aarch64-nostd.json)
used a std Criterion harness with a no_std codec, serial 10+4 and 16+8 GF16
reconstruction, one or four missing `ShardSlot` buffers, and byte-for-byte
preflight/postflight checks. The [probe source](../benchmarks/gf16-nostd-avx2/2026-11-01/nostd-fwht-probe.rs)
and lockfile were the same for both versions; release binaries were built from
the same source and target paths using Rust stable 1.99.1. This was a local
macOS AArch64 run without CPU isolation. A1/B1/B2/A2 compares the average of
two Criterion means per side; 20 samples, 0.3 s warmup and 0.8 s requested
measurement were used per case. Negative values mean lower latency.

| Shard size | Median latency change | Range across four cases |
| --- | ---: | ---: |
| 64 B | −8.68% | −10.65% to −4.64% |
| 4 KiB | −6.88% | −8.14% to −5.22% |
| 64 KiB | −1.71% | −2.97% to −1.00% |
| 1 MiB | −0.39% | −0.88% to +0.61% |

The slowest A1-to-A2 baseline change in absolute value was 4.23%; drift did
not gate this run. These results demonstrate the measured workload on this
machine, not a guarantee for all AArch64 CPUs or a std throughput improvement.

The [x86 no_std control](../benchmarks/gf16-locator-reduction/2026-11-01/x86-nostd.json)
covered the same 16 shapes on a Linux VM with guest CPUs reserved under a shared
lock. Across all cases, latency changes ranged from −0.50% to +1.05%.
The [std GFNI control](../benchmarks/gf16-locator-reduction/2026-11-01/x86-std.json)
covered 22 cold/warm recovery and encode cases, including 10+4 and 16+8,
64 B, 64 KiB and 1 MiB shards. The x86 controls used ten samples, 0.2 s
warmup and 0.6 s requested measurement. No competing heavy process was observed;
physical-host isolation was not verified. The exact baseline/candidate x86
benchmark binaries had byte-identical `.text` section contents for both
feature sets. On macOS AArch64 the std benchmark binaries had identical
`__TEXT,__text` and `__TEXT,__const` contents. These are build-specific
observations, not claims that the complete binaries are identical.

## Correctness and compatibility

The reduction is checked against `u64` division for every `u16` input at 11
edge factors. An independent original-form locator reference compares the full
65,536-element result for several erasure patterns, including the maximum
transform order. The AArch64 all-features workspace suite, excluding the fuzz package, passed,
including 370 xtask tests;
the separate no_std library suite passed 283 tests. The pinned no_std old/new probe passed 126 checks each on native
AArch64 and WASM; the std release probe passed 200 parity and bidirectional
cross-decoding configurations, 200 historical non-fast cases, 36 large GF8
cases and 12 6+2 cases. On native x86, 47 no_std GF16-focused tests passed.

The repository diagnostic generator binds exact generated bytes. Its two
expected dynamic-source digests were updated to the actual newly generated
value, and all 135 diagnostic tests passed without weakening the source or
output binding checks.
