## 修改及约束

旧 GF16 decode 工作区持有 FlatWork16、转换 scratch 和输出缩放 out_scratch。
转换/FFT 完成后，原始输入已进入独立的 work lanes；此后缩放仅从 work 读取，
写入 scratch 后立即转换到用户输出。两份 scratch 的有效使用阶段不重叠。

现在串行、多块并行和 no_std 恢复复用同一个 Vec。输出阶段以安全可变重借用表达
资源交接，每个目标复制完成后再覆盖该缓冲；下一块按原逻辑重新初始化有效范围。
没有新增 unsafe、公共 API、全局缓存、数据复制阶段或经验性调度阈值。
有限域运算、FFT 计划、输出顺序和临时恢复结果的发布边界保持。

4 MiB 的每线程 decode 堆缓冲预算保持，准入估算改为 work 加一个 scratch，
返回前仍按实际容量复核。原有 oversized 调用释放旧缓存且不保留超限工作区的规则保持。
减少真实占用后，部分配置会从超限变成预算内；这是资源减少带来的准入变化。
预算只覆盖 work 分配和 scratch 容量，不包含 plan、调用者分片或其他独立缓存。
immutable plan 的进程级 LRU 与 encoder 缓存规则没有变更。

## 资源对照

[完整记录及源码绑定](../benchmarks/global-review/2026-10-26/gf16-shared-scratch-resources.json)
包含每版本 15 个计数窗口：9 个冷工作区窗口、6 个缓存边界热调用窗口。
每个场景重复三次。完全相同的最终外部测试覆盖旧源码，实际收集全部记录后因预算断言
失败；当前实现全部通过。每个窗口后逐字节核对所有输出及 present 状态。

计数覆盖调用线程的 alloc/alloc_zeroed/realloc 次数与累计申请字节，max_parallel_jobs=1。
codec、编码输入及 ShardSlot 容器在窗口外准备；API 的临时输出、工作区和元数据留在
窗口内。计数不是存活内存、RSS、延迟或吞吐数据。

### 10+4，缺失 data 0，冷工作区

immutable plan 预热，每次在新的 OS 线程上执行首次 decode，避免复用已有可变工作区。
64 KiB 以上仍按原有 64 KiB 字节窗口分块，最后一项含 64 B 短尾。

| 分片长度 | 申请次数，前 → 后 | 累计申请字节，前 → 后 | 节省 |
| --- | ---: | ---: | ---: |
| 32,768 B | 4 → 3 | 622,592 → 589,824 | 32,768 B |
| 65,536 B | 4 → 3 | 1,245,184 → 1,179,648 | 65,536 B |
| 131,136 B | 4 → 3 | 1,310,784 → 1,245,248 | 65,536 B |

每个活跃工作区少一个 chunk scratch，当前每个完整 chunk 为 32,768 个 u16，
对应 65,536 B。并行路径使用同一个工作区帮助函数；没有采集所有工作线程的总体峰值。

### 40+16，64 个 FFT lanes，预算边界热调用

每个新线程先执行一次完整 decode，再计数第二次调用。

| 分片长度 | 申请次数，前 → 后 | 累计申请字节，前 → 后 | 缓存结果 |
| --- | ---: | ---: | --- |
| 64,000 B | 8 → 5 | 4,291,320 → 67,320 | 新工作区落入预算，可复用 |
| 65,536 B | 8 → 7 | 4,394,232 → 4,328,696 | 仍超限，继续释放 |

64,000 B 时旧工作区需要 `(64 + 2) * 64000 = 4,224,000 B`，超过 4,194,304 B；
共享后需要 `(64 + 1) * 64000 = 4,160,000 B`，因此热调用不再重建整套工作区。
65,536 B 时共享后的工作区仍为 4,259,840 B，超过预算，热调用继续申请本地工作区。
这两项仍包含请求输出和宽布局元数据；整个 API 没有变成零分配。

测试 stdout 的 cacheable 值是共享缓冲预算模型在两版上使用的同一预期判据，
不是对旧运行时缓存状态的探针采样。JSON 将它明确命名为 fits_shared_buffer_budget。
