## 保留分组，收敛准备阶段

原 GF16 并行恢复先为每个 chunk 构造一份 Vec<&mut [u8]>，再创建全部 chunk jobs，
最后由 par_chunks_mut 按有限作业预算切成连续组。尽管实际组数有限，预先保存的
引用表数量和 jobs 容量仍随 shard 的 chunk 数增长。

现在先计算同一分组，再用安全 chunks_mut 为每个目标切出各组的互不重叠输出区间。
每个 Rayon item 持有一个组的视图和全局 u16 起止位置，内部沿用原 chunk 循环，
以相对字节偏移写入本组。没有新增 unsafe、payload 复制、公共 API 或执行开关。

分组公式保持：C 为 chunk 数，B 为原作业上限与池大小的较小值（0 表示按池大小）；
每组 Q = ceil(C/B) 个 chunks，组数 J = ceil(C/Q)，且 J <= B。
原 par_chunks_mut(Q) 和新视图覆盖相同的连续 chunk 区间；并行激活条件、作业限制、
算术、chunk 大小、每组工作区租用、缓存政策和临时结果发布阶段保持。
这是输出引用表的准备方式变化，没有调参或选择新的调度粒度。

准备阶段的引用元数据由 O(C * 请求目标数) 收敛为 O(J * 请求目标数)。
每个请求目标的完整临时结果仍由原调用层分配，成功计算后才发布到调用者分片。
不能把引用元数据有界描述为整个 API 内存与 shard 长度无关。

固定 10+4，缺失 data 0、data 1、parity 10，调用完整 reconstruct。
短/长分片分别为 720,960 / 2,293,824 B，含 64 B 短尾，对应 12 / 36 个 64 KiB chunks。
这两种 chunk 数下，原公式在三种配置中分别产生 2、4、3 个组。

测试在只运行这一项的独立子进程中计数，本进程的全局 Rust allocator hooks 覆盖
调用线程和全部 Rayon worker 的 alloc/alloc_zeroed/realloc 请求。
显式构造专用池，通过 broadcast 在每个 worker 上预热同一 serial decode 工作区。
各完整并行 fixture 再预热一次，计数第二次调用；pool.install 返回后关闭窗口。
门禁和计数器使用 SeqCst 顺序，计数器只记录标量，不分配内存。

codec、已编码原文、调用者 ShardSlot 存储及池构造在窗口外。
计数前重新标记三个缺失目标并填为非零脏数据；计数后核对所有分片字节及 present 状态。
所有必要的临时输出和 API 元数据仍在窗口内。

候选分别为同样的 272、448、360 B。

扣除项严格按未修改的 reconstruct_leopard_impl 计算：每个请求的缺失目标分配一个
完整临时 Vec，本例共 3 * shard_len，即 2,162,880 / 6,881,472 B。
JSON 同时保留完整申请字节和扣除后的值；扣除后的值仍是累计请求量，包含其他元数据，
